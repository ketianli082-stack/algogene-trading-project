# ALGOGENE 基差套利策略：完整实验研究方案（V8.1 Baseline → Final Strategy）

> **状态：研究计划（NOT RUN）** ｜ **版本：1.0** ｜ **更新：2026-11-20**  
> **研究对象**：BTCUSD / BTCUSDM、ETHUSD / ETHUSDM，60-minute 数据  
> **源策略**：上传的 `crypto_basis_v8_1(1).py`；项目基准 V8.1（paired-exit correction）  
> **范围**：本文件是可执行的实验协议、记录规范和验收标准，**不是已完成的回测结果**。严禁填写未由平台或交易记录证实的业绩。

## 0. 研究目标与基本原则

### 0.1 核心研究问题

1. **经济可行性**：扣除可验证的四腿交易手续费、买卖价差、滑点及永续资金费率后，基差收敛策略是否仍有正的风险调整后收益？
2. **模型稳健性**：策略对历史窗口、Z-score、可执行开仓溢价、持仓期限和退出阈值是否敏感？效果是否依赖狭窄参数组合？
3. **资本效率**：在不改变核心信号的前提下，仓位、资金规模与杠杆如何影响收益、回撤、流动性及强平风险？
4. **风险边界**：异常基差扩张、单腿失败、数据过期、流动性消失及系统故障时，风险约束能否按设计生效？
5. **泛化能力**：在未参与模型选择的时间窗口和不同市场环境下，结论是否仍然成立？

### 0.2 研究顺序与依赖

```text
BAS-000 原始代码/平台/PnL口径核对，冻结 Baseline
     ↓
BAS-001 交易成本及资金费率（固定策略规则，只改变成本假设）
     ↓
BAS-002 参数敏感性（用合理成本作为共同假设）
     ↓
BAS-003 杠杆、资金配置与规模容量（固定所选交易规则）
     ↓
BAS-004 极端市场与订单执行压力测试（检验候选最终版）
     ↓
BAS-005 冻结最终策略，独立样本外评价、归因与报告
```

风险控制不是最后才加入：从 BAS-000 起就必须有安全的仓位/订单处理；BAS-004 是**验证并发现缺陷**。若压力测试导致修改代码，应返回受影响的阶段重测。成本实验首先用于确定现实边界，后续每个阶段都必须维持统一的成本口径。

### 0.3 数据使用与防过拟合

| 数据段 | 暂定期间（UTC） | 允许用途 | 禁止事项 |
| --- | --- | --- | --- |
| Development | 2021-01-01 — 2022-12-31 | 开发、故障修复、初步参数扫描 | 宣称为独立测试 |
| Validation | 2023-01-01 — 2024-12-31 | 选择成本情景和稳健参数、确定仓位 | 对其反复调参后宣称未见过 |
| Final Test | 2025-01-01 — 2025-12-31 | **冻结后的最终一次独立评价** | 使用该结果再改参数并继续叫“独立样本外” |
| Full Period | 2021-01-01 — 2025-12-31 | 图示与历史描述 | 替代 Final Test 证据 |

**独立性核查**：若 2025 年已在任何阶段用于选版本、调参或回看结果，须标记为 *previously inspected / contaminated holdout*。可将其称为 retrospective test，不得称严格独立 OOS；如需真正的 OOS，应预先锁定未来数据或开展前向模拟。所有区间需核对平台实际首末可用数据；每个运行允许预热但须披露预热是否产生交易。禁止跨回测区间遗留未平仓头寸而不说明。

### 0.4 冻结配置与可重复性

每次运行至少记录：研究编号、假设、策略源码 SHA256、Git commit、ALGOGENE Backtest ID、提交及完成时间、平台/数据版本、UTC 起止、四个品种、频率 60min、初始 NAV（建议基准 USD 1,000,000）、杠杆设置、short-selling、position netting、成本与无风险利率设置、订单/成交数量、平台原生结果、外部重算结果及二者差异。**不在代码中硬编码平台固定 `TradeCost` 去伪装百分比手续费。**

基准策略不覆盖；实验分支和配置独立保存。所有结论均需链接到原始 run ID、成交清单和日志。若数据/成本字段未确认，标记 `UNKNOWN`；若实验未完成，标记 `NOT RUN`。

## 1. BAS-000 — 基准正确性与绩效核对（所有实验前置）

**目的**：确定平台真正成交了什么，以及 `NAV / PnL / fees / funding` 分别包含什么。防止在不可信的基础上优化。

**源代码可确认的规则（与已完成实验结果严格区分）**：

| 元素 | V8.1 源码配置 |
| --- | --- |
| 方向 | 等币数量买入 spot，卖空对应 perpetual；BTC、ETH 两组 |
| 信号 | 使用先前 168 个同步小时中间价基差观察；样本标准差下限 2bp |
| 开仓 | z ≥ 2；以 bid/ask 计算的可执行开仓溢价 ≥ 30bp；相对 max(历史均值, 0) 的空间 ≥ 20bp |
| 仓位 | 每组 gross ≤ NAV 40%，总 gross ≤ NAV 80%；计划损失预算每组 ≤ NAV 0.25% |
| 退出 | 组合估算亏损 ≥ spot 单腿初始名义价值 75bp；或收敛且估算盈利；或 72 小时请求退出 |
| 冷却 | 退出后同组 6 小时 |
| 执行 | 使用同步报价检查、双腿委托与成交回调；双腿市场订单不具备原子性 |
| 计费 | 使用 bid/ask；没有额外完整的百分比手续费、资金费率及滑点模型 |
| 必要平台配置 | 四品种订阅、60min、USD 1m、leverage=1、short selling=True、position netting=False；源码要求合约 contractSize=1 |

**关键警示**：72h 是请求退出而不是保证平仓时间；报价缺失会延迟退出；`PAIR_DONE` 日志里 `gross_PnL_before_costs` 不能直接当作净利润；平台 Summary 可能为快照，需结合 fills、未平仓状态及年末审计。损失预算是入场时的规则，不代表实际最大亏损有硬上限。

**实验步骤**：
1. 锁定代码和配置，逐段运行 Development / Validation，另记录 全期描述性回测；核实四品种是否有相同时间戳、规格与有效报价。
2. 下载平台原生 Summary、成交记录、NAV 序列、订单拒绝/部分成交事件和控制台审计日志。
3. 按每笔真实成交建立 spot/永续交易腿匹配表；对照平台 PnL 和双腿总名义额；标记未平仓和未知成交。
4. 核对单位（币数量、合约大小、美元名义额、bp）、是否重复计费及平台 `TradeCost` 的实际字段含义。
5. 计算账户净值序列、最大回撤、日/月收益、交易数量、平均持仓、未对冲时间、退出原因占比；不可获得的指标保持缺失。
6. 做基本守恒检查：组合 PnL 与各腿 PnL 的差异应能由费用、资金费、估值或未平仓解释。

**通过标准**：代码/配置可复现；关键订单和 PnL 能对账；无无法解释的重大敞口；区分 realized 与 unrealized；缺失数据与中断明确列出。**未通过则暂停后续优化**。

**交付物**：`results/BAS-000/` 原始平台导出、配置快照、对账差异清单、各窗口收益/回撤图及问题日志。

## 2. BAS-001 — 交易成本和 Funding 稳健性实验（第一优先级）

### 2.1 问题与假设
- H1：成本越高，税费前/成本前的纸面收益与实际可实现净收益的差距越大。
- H2：在一组合理的手续费、滑点、Funding 情景下仍为正的组合比只在零成本下盈利的组合更具实盘意义。
- H3：双腿对冲不能消除资金费率及基差变化造成的全部风险。

### 2.2 费用口径（必须写清）
四个成交动作为：**现货买入、永续卖空、现货卖出、永续买回**；每个成交按自己的成交名义额收取成本。代码已用 spot ask / future bid 建仓，用 spot bid / future ask 测算平仓，因此 **bid-ask 已在报价中反映，不得再完整重复扣一次点差**。

以逐笔 fill 的美元名义额 `N_j = abs(q_j × price_j × contractMultiplier_j)` 计算：

```text
Commission = Σ_j N_j × commissionRate_j
AdditionalSlippage = Σ_j N_j × slippageRate_j    （若执行价尚未包含这一项）
GrossSpreadPnL = Σ_legs signedQty × (exitFill - entryFill) × multiplier
NetPnL_noFunding = GrossSpreadPnL - Commission - AdditionalSlippage - otherVerifiedCosts
NetPnL_withFunding = NetPnL_noFunding + SignedNetFunding
```

**Funding**：对永续头寸按实际持有区间和方向计，正资金费率下做空通常收到资金费，负资金费率下做空通常支付；金额以实际交易场所公布的结算规则为准。项目已有 `docs/BAS-001_年度平均Funding方案.md` 和年度费率空白模板：主要分析可按 **BTC/ETH 分币种、分年份均值**进行持仓分段估算，同时独立报告**不含 Funding**的主结果；年度均值不等于逐次结算真实资金流，跨年必须拆分。**严禁填造年度历史均值或将人工测试值称历史数据**。

### 2.3 实验设计

| 维度 | 水平（研究情景，不是经纪商报价） | 控制 |
| --- | --- | --- |
| 单边手续费 | 0 / 2 / 5 / 10 bp | 不改变入场、止损、持仓和仓位 |
| 额外单边滑点 | 0 / 2 / 5 / 10 bp | 明确是否已含在模拟 fill 中 |
| Funding | 0；已核实的 BTC/ETH 年度均值；资金费率不利敏感性 | 不凭空宣称真实年均 |
| 价差恶化 | 基准 bid/ask；扩大价差情景 | 若改变 fill，应清楚标示为执行模型情景 |
| 成本组合 | 基准、温和、偏高、极端 | 尽量采用分层/小型矩阵，避免笛卡尔积过大 |

**先进行 replay/post-trade 费用归因**：同一份成交清单，独立计算净收益和收益转负的 break-even cost；这回答“同样交易如果收这些费会怎样”。**再做含成本反馈的策略重跑**：如果平台不能准确表达百分比收费，构建经校验的账本/执行模拟或外部复算，并明确它不能完全替代平台原生 NAV、保证金与订单执行。费用会影响 NAV、仓位和入场过滤条件，因此最终版必须在一致费用假设下进行闭环回测，不能将事后扣费等同完整仿真。

### 2.4 输出指标
总手续费、额外滑点、净 Funding、每对平均往返成本、单笔净获利、盈利交易占比、利润因子、扣费后 NAV/Sharpe/MaxDD、月度亏损月份占比、break-even 成本 bp，以及 BTC/ETH 分组差异。

**判定**：成本假设可追溯；四个成交方向、合约单位正确；无双重扣费；若合理成本下长期失效，不直接进入“提高杠杆”步骤，应优先复核信号和成交质量。不要预设收益必须为正。

**交付**：`results/BAS-001/` 成本情景矩阵、单笔费用归因、净值对比及成本阈值图；记录 Funding 资料来源与适用期间。

## 3. BAS-002 — 参数敏感性与模型稳健性（第二优先级）

### 3.1 目的
辨别策略是否真正依赖可解释的价差均值回归，而非参数偶然选中某段历史。此阶段**固定 BAS-001 选定的成本口径**；若候选模型将成本作为开仓门槛，须另外与“纯事后扣费版本”对照。

### 3.2 单因子实验矩阵（建议）

| 参数 | Baseline | 候选水平 | 评价原因 |
| --- | ---: | --- | --- |
| prior observations | 168 | 72 / 168 / 336 小时 | 自适应程度与信号滞后 |
| ENTRY_Z | 2.0 | 1.5 / 2.0 / 2.5 / 3.0 | 信号稀疏性与价差极端度 |
| MIN_ENTRY_BPS | 30 | 20 / 30 / 40 / 50 bp | 可成交价差覆盖成本 |
| MIN_EDGE_BPS | 20 | 10 / 20 / 30 / 40 bp | 相对历史均值的保守程度 |
| MAX_HOLD_HOURS | 72 | 24 / 48 / 72 / 120 h | 收敛机会与库存风险 |
| STOP_BPS | 75 | 50 / 75 / 100 bp | 亏损控制与过早退出 |
| PAIR_GROSS_CAP | 40% | 本阶段**固定** | 留给资金实验 |
| PAIR_RISK_CAP | 0.25% | 本阶段**固定** | 留给风险/资金实验 |

每组只改变一个参数；若初步看到稳健“平台区间”，再仅对关键两个参数做小范围二维网格，不做无上限挖掘。窗口变化要同步检查 `MAX_WINDOW_HOURS` 的合理性，不能简单调大 WINDOW 而因 210h 有效范围过滤误伤 336h 实验。

**设计纪律**：
1. 先明确 primary objective（建议验证集**扣费后 Sharpe**，同时设最大回撤/成交样本量约束）；总收益、Profit Factor、成交次数作为辅指标。
2. 所有参数实验采用相同时间段和成本模型；不同版本记录完整源码 hash。
3. 绘制参数—净收益、Sharpe、MaxDD、交易数的曲线与热力图；同时观察 BTC/ETH 是否方向一致。
4. 设置最低成交样本量和不确定性报告；低交易数的高 Sharpe 不视为充分证据。
5. 优先选结果稳定的**宽区域**而非单个最高点；只用 Development / Validation 做最终选择。
6. 保留原 V8.1 参数为对照；如改动信号，登记为候选 Final，而不是覆盖 Baseline。

**特别说明**：若在 Validation 上反复大幅搜索，验证集也会被“用旧”。需报告测试次数、选择过程，或使用 walk-forward 分段；最终测试集仍应冻结保留。

**交付**：`results/BAS-002/` 参数扫描 CSV、图表、候选选择理由和未选方案。

## 4. BAS-003 — 杠杆、资金配置与容量（第三优先级）

### 4.1 三件事必须分开
- **账户杠杆设置**：平台/经纪商的保证金与融资参数。
- **实际头寸名义敞口**：代码 `PAIR_GROSS_CAP=40%` 与 `TOTAL_GROSS_CAP=80%` 可能使提高账户杠杆**完全不增加交易量**。
- **资金效率**：现金闲置、保证金占用、可用资金缓冲、双腿跨交易场所转账/结算。

因此不能简单把 1x 回测收益乘以 2 就称 2x 结果，更不能把 gross exposure / NAV 与借款杠杆混为一谈。

### 4.2 两轴实验

| 实验轴 | 建议水平 | 固定项 |
| --- | --- | --- |
| A 账户杠杆 | 1.0 / 1.5 / 2.0 / 3.0x（仅平台支持且有合理保证金规则时） | 头寸上限与核心信号 |
| B Gross 上限 | 40/80%（原版）；例如 20/40%、60/120%（仅在真实可行条件下） | 杠杆设定、信号与成本 |
| C 账户起始资金 | USD 10k / 100k / 1m / 10m | 按真实合约最小量、手续费、冲击成本缩放 |

对 B 中的高敞口情景，先计算是否会触碰可用余额、配对风险预算和实际平台保证金规则；**不能假定某个平台允许超 100% gross 且完全无融资成本**。只有规则可被验证时运行杠杆情景；否则将其作为理论上界并注明未验证。

### 4.3 核心量化指标
- 实际 gross/NAV 时间序列（均值、P95、最大值），净币数量敞口和对冲偏离；
- available balance、margin used、free margin、最大保证金占用与临界强平距离（必须采用真实合约/经纪商规则）；
- 总收益、扣费后收益、Sharpe、Sortino、MaxDD、Calmar、最坏月收益；
- trade count、每笔名义额、最低交易规模、拒单率、成交占比、现金/资金缓冲；
- 随 AUM 扩大，估计 volume / orderbook depth、滑点、容量和潜在冲击成本（无深度数据则标注“无法可靠估计容量”）。

**最低资金** = 至少同时满足四腿最小下单量、双腿持仓/保证金、额外亏损缓冲、手续费和执行安全余额；不能直接把 USD 10k 当作经验证最低规模。仓位尺寸 `floor(qty × 10000)/10000` 也不等于每个实际交易场所的最小量。

**判定**：优先选择在保守保证金与费用假设下仍有可接受回撤、充足可用余额和可操作订单规模的配置，不能按绝对收益最高选杠杆。

**交付**：`results/BAS-003/` 杠杆×敞口对比、AUM容量表、资金使用率时序和最低资金核算表。

## 5. BAS-004 — 风险压力测试与异常执行（第四优先级）

**目的**：验证 V8.1 “双腿同期新鲜报价后才请求成对平仓”的安全改善，同时如实暴露仍存在的非原子成交风险。此部分包含历史情景与工程故障注入两个层面，不能用普通历史回测代替。

| 场景编号 | 冲击/故障 | 重点观察 | 合格的安全行为 |
| --- | --- | --- | --- |
| S1 | 基差持续扩大，不收敛，直到最大持仓时限 | 最大账面损失、超期持仓 | 按规则提出退出；超期如实记录 |
| S2 | 一条腿开仓成功，另一腿拒单/延迟 | 净币敞口、异常订单处理 | 停止新开仓、触发可追踪的解除对冲流程 |
| S3 | 平仓时一条腿报价过期 | quote-wait 小时、双腿剩余状态 | 对完整对冲优先等待同期有效报价，不故意拆腿 |
| S4 | 一条腿平仓订单被拒，另一腿已成交 | 未对冲时间、重试和重复成交 | 受控重试/停止，并提示人工对账 |
| S5 | `sendOrder` 抛异常、返回状态不确定 | 重复提交、未知仓位 | 保守冻结新开仓；不盲目重发未知订单 |
| S6 | 部分成交/成交数量不匹配 | 未对冲数量、未解决订单 | 显式 halt/人工核对；不声称自动恢复成功 |
| S7 | 市场 Bid/Ask 突然扩大，附加滑点上升 | 净值回撤、退出质量 | 实际计入成本，报告订单恶化 |
| S8 | 价格剧烈跳空/流动性枯竭 | 止损超限、保证金/强平风险 | 披露止损非保证，识别无法成交情形 |
| S9 | 连续数据中断、长于 6h 的观测缺口 | 信号重置、持仓延长 | 不用过时价格伪生成平仓 |
| S10 | 两组同时触发信号、可用余额减少 | 资金预约与重复订单 | 保证 pair 与 portfolio 资金约束生效 |

### 5.1 压力强度与场景来源
- **历史回放**：选择样本中波动、价差变化或流动性最不利时段，以日期和真实数据证据标记；不得直接为“极端月份”编造市场事实。
- **假设冲击**：例如附加滑点 +5/+10/+20bp、报价延迟 1/3/6/24h、基差再扩大 25/50/100bp。这些是预先登记的**假设值**，并非真实历史分布分位数。
- **故障注入**：使用 stub/fake execution callback 重现拒单、部分成交、异常状态、同步回调和晚到成交。离线故障注入证明逻辑分支，不等于真实 ALGOGENE 撮合/经纪商执行能力。

### 5.2 必须披露的限制
V8.1 不能保证两笔市价单原子成交；即使两个报价同一小时，也不代表严格同期撮合。72h 不保证准时平仓；止损是触发请求不是成交价格保证；未确认订单、错误成交可能需要人工处理；长期双腿报价中断仍可能延长持仓风险。

### 5.3 检验与验收
记录每个案例的：初始状态、冲击注入时点、实际订单/成交回调、策略动作、`halt_entries`、敞口最大值、未对冲持续小时、平仓等待小时、PnL/MaxDD、是否需人工恢复。明确结果为 `PASS / FAIL / UNKNOWN / NOT RUN`；任何关键 FAIL 必须建立修复编号，并重跑 BAS-000 受影响核对、BAS-001 成本及 BAS-005 测试前验证。不能因为日志显示 `PAIR_EXIT` 就断言实际已平仓。

**交付**：`results/BAS-004/` 场景矩阵、故障回调、日志片段、恢复与残余风险清单。
